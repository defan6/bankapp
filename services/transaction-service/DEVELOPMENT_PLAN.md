### Декомпозиция Задачи: Разработка Transaction Service

Это детальный план разработки микросервиса `transaction-service`, основанный на архитектурных документах проекта и принципах Saga-оркестрации.

---

### Этап 1: Создание API и запуск транзакции

**Цель:** Реализовать API для инициации перевода, провести валидацию и атомарно сохранить начальное состояние транзакции, запустив "Сагу".

*   **1.1. Настройка проекта:**
    *   **Задача:** Создать базовый Spring Boot проект с необходимыми зависимостями: Spring Web, Spring Data JPA, PostgreSQL Driver, Spring for Apache Kafka, Spring Cloud OpenFeign.
    *   **Контрольная точка:** Пустой проект успешно запускается.

*   **1.2. Создание моделей данных:**
    *   **Задача:** В пакете `model` создать две JPA-сущности:
        1.  `Transaction`: для хранения информации о переводе (`id`, `fromAccountId`, `toAccountId`, `amount`, `status`, `createdAt` и т.д.).
        2.  `OutboxEvent`: для реализации паттерна "Transactional Outbox" (`id`, `topic`, `payload`, `createdAt`).
    *   **Задача:** Создать соответствующие JPA-репозитории (`TransactionRepository`, `OutboxEventRepository`).
    *   **Контрольная точка:** Код компилируется, Liquibase/Hibernate создает таблицы при запуске.

*   **1.3. Реализация синхронной валидации:**
    *   **Задача:** Создать Feign-клиент (`AccountServiceClient`) для обращения к `account-service`.
    *   **Задача:** В клиенте определить метод для получения информации о счете (`GET /api/accounts/{accountId}`).
    *   **Контрольная точка:** Feign-клиент может быть заинжектирован в другой сервис.

*   **1.4. Реализация API-контроллера и сервиса:**
    *   **Задача:** Создать `TransactionController` с эндпоинтом `POST /api/transactions/transfer`.
    *   **Задача:** Создать `TransactionService` с методом `initiateTransfer`.
    *   **Задача:** В методе `initiateTransfer` реализовать **ключевую логику**:
        1.  Получить `userId` инициатора из заголовка `X-User-Id`.
        2.  Вызвать `AccountServiceClient` для валидации счета списания (проверить, что он существует и принадлежит `userId`).
        3.  Вызвать `AccountServiceClient` для валидации счета зачисления (проверить, что он существует).
        4.  Если валидация провалена — вернуть ошибку `400 Bad Request` или `403 Forbidden`.
        5.  Если все хорошо, в **одной транзакции (`@Transactional`)**:
            *   Сохранить новую `Transaction` в базу со статусом `PENDING`.
            *   Сохранить `OutboxEvent` с "полезной нагрузкой" для команды `DebitFunds`.
        6.  Вернуть ответ `202 Accepted` с `transactionId`.
    *   **Контрольная точка:** POST-запрос на эндпоинт успешно создает записи в таблицах `transactions` и `outbox` и возвращает `202`.

### Этап 2: Публикация событий из Outbox

**Цель:** Реализовать механизм, который гарантированно доставляет события из таблицы `outbox` в Kafka.

*   **2.1. Настройка Kafka Producer:**
    *   **Задача:** Сконфигурировать `KafkaProducer` и `KafkaTemplate` в приложении.

*   **2.2. Реализация Outbox Publisher:**
    *   **Задача:** Создать компонент (`@Component`), который с заданной периодичностью (`@Scheduled`) будет опрашивать таблицу `outbox`.
    *   **Задача:** Для каждого найденного события: отправить его в Kafka с помощью `KafkaTemplate`, а после успешной отправки — удалить событие из таблицы `outbox`.
    *   **Контрольная точка:** После выполнения Этапа 1.4, через несколько секунд в топике Kafka (`account-commands`) появляется команда `DebitFunds`.

---

### Этап 3: Оркестрация "Саги"

**Цель:** Реализовать логику конечного автомата, который реагирует на события из Kafka и двигает "Сагу" вперед или запускает компенсации.

*   **3.1. Настройка Kafka Consumer:**
    *   **Задача:** Сконфигурировать `KafkaConsumerFactory` для прослушивания событий.

*   **3.2. Реализация обработчиков событий:**
    *   **Задача:** Создать компонент-оркестратор (`SagaOrchestrator`) с методами, аннотированными `@KafkaListener`, для прослушивания топика `account-events`.
    *   **Задача:** Реализовать обработку следующих событий:
        *   **`FundsDebited`**: Найти транзакцию по `correlationId`. Если статус `PENDING`, отправить команду `CreditFunds` (через запись в `outbox`).
        *   **`FundsCredited`**: Найти транзакцию. Если она в правильном статусе, поменять его на `COMPLETED` и отправить финальное событие `TransactionCompleted` (через `outbox`).
        *   **`DebitFailed`**: Найти транзакцию, поменять статус на `FAILED`, отправить финальное событие `TransactionFailed` (через `outbox`).
        *   **`CreditFailed`**: Найти транзакцию, поменять статус на `FAILED`, отправить **компенсирующую** команду `RefundDebit` (через `outbox`), а затем событие `TransactionFailed` (через `outbox`).
    *   **Контрольная точка:** Полный цикл перевода (отправка-списание-зачисление-завершение) проходит успешно, и в соответствующих топиках появляются все команды и события.

### Этап 4: Тестирование и Завершение

**Цель:** Обеспечить качество и надежность кода, добавить вспомогательные эндпоинты.

*   **4.1. Эндпоинт для статуса:**
    *   **Задача:** Реализовать эндпоинт `GET /api/transactions/{transactionId}`, который возвращает текущий статус транзакции из базы данных.

*   **4.2. Написание тестов:**
    *   **Задача:** Написать **Unit-тесты** для `TransactionService`, `TransactionController`, `SagaOrchestrator`, используя моки (Mockito) для репозиториев, Feign-клиента и Kafka-продюсера/консьюмера.
    *   **Задача:** Написать **интеграционные тесты** с использованием `@SpringBootTest` и `Testcontainers` для запуска реальных экземпляров PostgreSQL и Kafka. Протестировать несколько сценариев:
        1.  Успешный перевод.
        2.  Сбой из-за недостатка средств.
        3.  Сбой из-за невалидного счета получателя (проверка на этапе 1).
        4.  Сбой зачисления с последующей компенсацией.
    *   **Контрольная точка:** Все тесты успешно проходят.
