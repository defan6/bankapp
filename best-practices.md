# Best Practices и Стандарты Разработки "Core Banking System 2.0"

Этот документ определяет набор правил и лучших практик, которым должен следовать каждый разработчик в этом проекте. Цель — обеспечить высокое качество кода, его консистентность и простоту поддержки.

---

### 1. Качество Кода и Стиль

1.  **Стиль Кода:** Придерживаемся стандартного стиля Java. Используйте автоматическое форматирование в вашей IDE (например, Google Java Style Guide).
2.  **Иммутабельность:** Отдавайте предпочтение иммутабельным объектам. Для DTO (Data Transfer Objects) используйте **Java Records**, где это возможно. Это делает код более предсказуемым и потокобезопасным.
3.  **Осмысленные Имена:** Имена переменных, методов и классов должны быть четкими и самодокументируемыми. Избегайте сокращений (например, `usrSrv` -> `userService`).
4.  **Никаких "Магических" Значений:** Все строковые литералы и числа, которые не являются очевидными, должны быть вынесены в константы.
5.  **Логирование:**
    *   Используйте SLF4J (стандарт в Spring Boot).
    *   Логируйте на уровне `INFO` ключевые бизнес-события ("Пользователь зарегистрирован", "Транзакция инициирована").
    *   Используйте `DEBUG` для технической отладочной информации.
    *   Используйте `WARN` для некритичных, но потенциально проблемных ситуаций.
    *   Используйте `ERROR` для серьезных сбоев, требующих внимания.
    *   **Всегда** используйте параметризованное логирование: `log.info("User {} created account {}", userId, accountId);`, а **не** конкатенацию строк: `log.info("User " + userId + " created account...");`.

### 2. Проектирование API (REST)

1.  **Ресурсы в URI:** Используйте существительные во множественном числе для именования ресурсов (например, `/api/users`, `/api/accounts`).
2.  **Стандартные HTTP-методы:**
    *   `GET`: Получение ресурсов.
    *   `POST`: Создание нового ресурса.
    *   `PUT`/`PATCH`: Обновление существующего ресурса.
    *   `DELETE`: Удаление ресурса.
3.  **Стандартные Коды Ответа HTTP:**
    *   `200 OK`: Успешный `GET`, `PUT`, `PATCH`.
    *   `201 Created`: Успешный `POST`.
    *   `202 Accepted`: Запрос принят в обработку (для асинхронных операций, как наша транзакция).
    *   `204 No Content`: Успешный `DELETE`.
    *   `400 Bad Request`: Ошибка валидации на стороне клиента.
    *   `401 Unauthorized`: Проблема с аутентификацией (невалидный JWT).
    *   `403 Forbidden`: У пользователя нет прав на это действие.
    *   `404 Not Found`: Ресурс не найден.
    *   `500 Internal Server Error`: Ошибка на стороне сервера.
4.  **DTO для API:** **Никогда** не используйте JPA-сущности (`@Entity`) напрямую в API-контроллерах. Всегда создавайте отдельные DTO-классы для запросов и ответов. Это разделяет ваш внутренний домен и внешний контракт.
5.  **Единообразный Формат Ошибок:** Используйте `@RestControllerAdvice` для создания единого формата ответа при ошибках.

### 3. Асинхронное Взаимодействие (Kafka)

1.  **Идемпотентность Консьюмеров:** Это **обязательное** правило. Каждый обработчик сообщения Kafka должен быть идемпотентным. Если он получит одно и то же сообщение дважды, система не должна сломаться (например, не должно быть двойного списания денег). Реализуйте это через проверку уникального `eventId`/`commandId`.
2.  **Версионирование Событий:** События — это публичный контракт. Развивайте их осторожно, используя версию в имени типа (`UserRegistered.v1`).
3.  **Dead-Letter Queue (DLQ):** Для всех консьюмеров должен быть настроен механизм DLQ. Если сообщение не удается обработать после нескольких попыток, оно должно отправляться в отдельный "мертвый" топик для анализа, а не блокировать обработку всей очереди.
4.  **Корреляционный ID:** Все события, относящиеся к одному бизнес-процессу (нашей саге), должны содержать один и тот же `correlationId` (`transactionId`).

### 4. База Данных и Персистентность

1.  **Миграции только через Liquibase:** Схема базы данных управляется **исключительно** через файлы миграций Liquibase. В `application.yml` свойство `spring.jpa.hibernate.ddl-auto` должно быть установлено в `validate` или `none`.
2.  **Короткие Транзакции:** Границы транзакций (`@Transactional`) должны быть как можно меньше и находиться на методах сервисного слоя, изменяющих состояние.
3.  **Каждый Сервис Владеет Своей БД:** Никаких прямых запросов из одного сервиса в базу данных другого. Взаимодействие — только через API (синхронное) или события (асинхронное).

### 5. Конфигурация

1.  **Никаких Секретов в Коде:** Все чувствительные данные (секреты JWT, пароли) должны быть вынесены из кода. В нашем проекте мы используем переменные окружения, что приемлемо. В реальном production-проекте следовало бы использовать Vault (например, HashiCorp Vault).
2.  **Профили для Окружений:** Активно используем профили Spring (`local`, `docker`) для разделения конфигурации под разные окружения.

### 6. Безопасность

1.  **Аутентификация на Границе:** `API Gateway` — единственный, кто отвечает за проверку JWT токенов.
2.  **Авторизация в Сервисах:** Каждый внутренний сервис отвечает за проверку прав доступа (`Этот пользователь может видеть этот счет?`). Он доверяет заголовку `X-User-Id`, но сам принимает решение об авторизации.
3.  **Хеширование Паролей:** Пароли хранятся только в виде хеша, полученного с помощью `BCryptPasswordEncoder`.

### 7. Тестирование

1.  **Unit-тесты:** Покрывают логику отдельных классов (особенно в сервисном слое) с использованием моков (Mockito). Должны быть быстрыми.
2.  **Интеграционные тесты:** Проверяют взаимодействие внутри одного сервиса (контроллер -> сервис -> репозиторий). Используют `@SpringBootTest` и, в идеале, Testcontainers для поднятия реальной БД в тесте.
3.  **E2E (End-to-End) тесты:** Для этого проекта достаточно ручного тестирования ключевых сценариев через `Swagger UI` или Postman.
