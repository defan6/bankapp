# Детальный План Разработки "Core Banking System 2.0" (Версия 3.0)

**Версия:** 3.0
**Дата:** 21.12.2025

Этот документ описывает детальную последовательность разработки с разбивкой на подзадачи и точки проверки (break points)
для каждой из них. План составлен с учетом всех ранее созданных артефактов (`api-spec`, `db-schema`, `event-contracts`,
`patterns-guide`).

---

### Этап 0: Фундамент (Выполнен)

**Цель:** Подготовлена и запущена полностью сконфигурированная, но "пустая" система.
**Break Point:** Команда `docker-compose up --build` успешно запускает все контейнеры, Liquibase создает начальную схему
во всех сервисах.

---

### Этап 1: Идентификация и Безопасность

**Цель:** Реализовать регистрацию, вход и безопасный доступ к API через `api-gateway`.
**Фокус:** `user-service`, `api-gateway`.

* **1.1. Реализация Модели Данных в `user-service`**
    * **Задача:** Создать JPA-сущность `User` в пакете `model` в соответствии с `database-schema-definitions.md`.
    * **Breakpoint:** Код компилируется. Сущность `User` имеет все поля и аннотации JPA.

* **1.2. Реализация Репозитория в `user-service`**
    * **Задача:** Создать интерфейс `UserRepository` в пакете `repository`, наследуемый от `JpaRepository<User, UUID>`.
      Добавить метод `findByEmail(String email)`.
    * **Breakpoint:** Код компилируется. Можно запустить пустой тест, который инжектит (`@Autowired`) `UserRepository`,
      и он проходит.

* **1.3. Реализация DTO и Обработки Исключений в `user-service`**
    * **Задача:** В пакете `dto` создать классы/записи `RegisterUserRequest`, `LoginRequest`, `AuthResponse`.
    * **Задача:** В пакете `exception` создать `@RestControllerAdvice` класс для централизованной обработки исключений (
      например, для `UserAlreadyExistsException`).
    * **Breakpoint:** Все классы созданы и компилируются.

* **1.4. Реализация Сервисного Слоя в `user-service`**
    * **Задача:** Создать `UserService` с методом `register`, который проверяет существование пользователя, хеширует
      пароль через `PasswordEncoder` и сохраняет сущность.
    * **Задача:** Создать `JwtTokenProvider` для генерации JWT.
    * **Задача:** Реализовать сервис `AuthenticationService` с методом `login`, который проверяет пароль и возвращает
      JWT.
    * **Breakpoint:** Unit-тесты для `UserService` и `AuthenticationService` с использованием Mockito для репозитория
      успешно проходят.

* **1.5. Настройка Spring Security в `user-service`**
    * **Задача:** Создать `SecurityConfig`, определить бин `PasswordEncoder`, настроить `AuthenticationManager` и
      цепочку фильтров (`filterChain`), разрешив доступ к `/api/users/register` и `/api/users/login`.
    * **Breakpoint:** Приложение запускается. Запрос к защищенному эндпоинту без токена возвращает `401 Unauthorized`.

* **1.6. Реализация Контроллера в `user-service`**
    * **Задача:** Создать `UserController` в пакете `controller` с эндпоинтами, которые вызывают соответствующие методы
      сервисов.
    * **Breakpoint:** Интеграционный тест (с `@SpringBootTest`) для регистрации и логина успешно проходит. Swagger UI
      показывает эндпоинты.

* **1.7. Реализация Фильтра Безопасности в `api-gateway`**
    * **Задача:** Создать глобальный фильтр (Global Filter), который валидирует JWT для всех входящих запросов, кроме
      публичных.
    * **Задача:** В случае успеха валидации, фильтр добавляет заголовок `X-User-Id` в запрос.
    * **Breakpoint:** Запрос к любому эндпоинту через `api-gateway` (порт `8080`) с валидным токеном проходит, без
      токена — возвращает `401`.

### Этап 2: Управление Счетами

**Цель:** Дать пользователям возможность создавать и просматривать свои банковские счета.
**Фокус:** `account-service`.

* **2.1. Реализация Модели и Репозитория**
    * **Задача:** Создать сущность `Account` и интерфейс `AccountRepository` в `account-service`.
    * **Breakpoint:** Код компилируется.

* **2.2. Реализация Сервиса и Контроллера**
    * **Задача:** Создать `AccountService` и `AccountController`. В логике использовать `X-User-Id` из заголовка для
      всех операций.
    * **Задача:** Реализовать эндпоинты `POST /api/accounts` (создание), `GET /api/accounts` (список) и
      `GET /api/accounts/{accountId}` (для валидации).
    * **Breakpoint:** Через API Gateway, пользователь с токеном может создавать и видеть **только свои** счета. Запрос
      `GET` на конкретный счет работает.

### Этап 3: Ядро Транзакции (Сага и Outbox)

**Цель:** Реализовать отказоустойчивый процесс перевода денег.
**Фокус:** `transaction-service`, `account-service`.

* **3.1. Реализация Моделей в `transaction-service`**
    * **Задача:** Создать JPA-сущности `Transaction` и `OutboxEvent` в пакете `model`.
    * **Breakpoint:** Код компилируется.

* **3.2. Реализация API Транзакций**
    * **Задача:** В `transaction-service` реализовать эндпоинт `POST /api/transactions/transfer`.
    * **Задача:** Сервис должен вызывать `AccountServiceClient` (Feign) для валидации счетов и владельца.
    * **Задача:** Реализовать **атомарную** запись в таблицы `transactions` (статус `PENDING`) и `outbox` в рамках одной
      транзакции БД.
    * **Breakpoint:** `POST` запрос на `/api/transactions/transfer` создает записи в обеих таблицах (`transactions` и
      `outbox`) и возвращает `202 Accepted`.

* **3.3. Реализация Паттерна Outbox Publisher**
    * **Задача:** В `transaction-service` и `account-service` создать компонент (`@Scheduled`), который периодически
      опрашивает свою `outbox` таблицу.
    * **Задача:** Реализовать логику отправки найденных событий в Kafka и их последующего удаления (или пометки как "
      отправлено").
    * **Breakpoint:** После ручной вставки записи в `outbox`, в логах сервиса появляется сообщение об отправке, а в
      Kafka-топике появляется соответствующее сообщение.

* **3.4. Реализация Обработчиков Команд в `account-service`**
    * **Задача:** Создать Kafka-консьюмер (`@KafkaListener`) для команд `DebitFunds` и `CreditFunds`.
    * **Задача:** Реализовать **идемпотентность** обработчиков (например, через проверку `commandId` в Redis).
    * **Задача:** Реализовать логику изменения баланса и запись ответного события в `outbox`.
    * **Breakpoint:** При получении команды из Kafka, баланс счета меняется, и в `outbox` таблице `account-service`
      появляется ответное событие. Повторное получение той же команды не меняет баланс.

* **3.5. Реализация Оркестратора Саги в `transaction-service`**
    * **Задача:** Создать Kafka-консьюмеры для прослушивания ответных событий от `account-service`.
    * **Задача:** Реализовать логику конечного автомата (Saga): получил `FundsDebited` -> отправь `CreditFunds`; получил
      `FundsCredited` -> измени статус транзакции на `COMPLETED` и запиши финальное событие в `outbox`.
    * **Задача:** Реализовать логику компенсаций: получил `CreditFailed` -> отправь команду `RefundDebit`.
    * **Breakpoint:** Полный цикл перевода денег успешно проходит через все этапы и завершается со статусом `COMPLETED`.

### Этапы 4, 5, 6 (Кратко, для полноты)

* **Этап 4: Запросы и Уведомления**
    * **4.1. Реализация `history-service`:** Создать сущность, идемпотентный консьюмер и эндпоинт. **Breakpoint:**
      История пополняется после транзакции.
    * **4.2. Реализация `notification-service`:** Создать идемпотентные консьюмеры и логировать получение событий. *
      *Breakpoint:** Сервис логирует события о регистрации и транзакциях.

* **Этап 5: Дополнительный Функционал**
    * **5.1. Реализация `analytics-service`:** Настроить консьюмер с пакетной вставкой в ClickHouse. **Breakpoint:**
      Транзакции появляются в ClickHouse.
    * **5.2. Реализация `scheduler-service`:** Настроить Quartz Job с персистентным хранилищем и эндпоинты управления. *
      *Breakpoint:** Запланированный платеж исполняется один раз в указанное время.

* **Этап 6: Observability и Финализация**
    * **6.1. Настройка Мониторинга:** Настроить дашборды и алерты в Grafana. **Breakpoint:** Приходят алерты о тестовых
      сбоях.
    * **6.2. Настройка Трассировки:** Убедиться в корректности сквозной трассировки. **Breakpoint:** В Jaeger/Tempo
      видна полная цепочка вызовов, включая переходы через Kafka.
    * **6.3. Финальное ревью:** Рефакторинг, документирование, расширение покрытия тестами. **Breakpoint:** Проект
      готов.
