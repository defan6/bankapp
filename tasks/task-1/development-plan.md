# План Разработки Проекта "Core Banking System 2.0" (Версия 2.0)

**Версия:** 2.0
**Дата:** 21.12.2025

Этот документ описывает последовательность этапов разработки проекта, их цели, основные задачи и критерии завершения (break points). Эта версия дополнена с учетом лучших практик и ранее упущенных деталей.

---

### Этап 0: Фундамент и Инфраструктура

**Цель:** Подготовить и запустить полностью сконфигурированный, но "пустой" проект. Убедиться, что вся инфраструктура и скелет приложения работают вместе.

**Задачи:**
1.  Создание всей проектной документации (*сделано*).
2.  Настройка Gradle-сборки, Docker Compose, Liquibase, `application.yml` с профилями (*сделано*).
3.  Создание и верификация начальной схемы БД через Liquibase-миграции (*сделано*).
4.  **Новое:** Настройка базового CI/CD пайплайна (например, в GitHub Actions), который при каждом коммите в `main` запускает сборку (`./gradlew build`) и прогоняет все тесты (`-x test` убрать). Это гарантирует, что основной код всегда в рабочем состоянии.

**Break Point:**
*   Команда `docker-compose up --build` успешно запускает все контейнеры.
*   Liquibase корректно применяет миграции во всех 5 сервисах.
*   CI/CD пайплайн успешно проходит на "пустом" проекте.

### Этап 1: Идентификация и Безопасность

**Цель:** Реализовать регистрацию, вход и безопасный доступ к API.

**Фокус:** `user-service`, `api-gateway`.

**Задачи:**
1.  **В `user-service`:**
    *   Создать DTO для регистрации и аутентификации (`RegisterUserRequest`, `LoginRequest`, `AuthResponse`).
    *   Создать JPA-сущность `User`.
    *   Создать `UserRepository`.
    *   Реализовать `UserService` с логикой хеширования паролей (`PasswordEncoder`).
    *   Реализовать `JwtTokenProvider` для генерации/валидации JWT.
    *   Настроить Spring Security.
    *   Создать `UserController` для эндпоинтов `/register` и `/login`.
    *   **Новое:** Создать централизованный обработчик исключений (`@RestControllerAdvice`) для корректной отправки ошибок (например, `409 Conflict` при дублировании email).
2.  **В `api-gateway`:**
    *   **Новое:** Реализовать глобальный фильтр безопасности (Global Filter) для валидации JWT токенов, который:
        *   Пропускает публичные эндпоинты.
        *   Валидирует токен для защищенных эндпоинтов.
        *   В случае успеха, добавляет заголовок `X-User-Id` в запрос к внутреннему сервису.
        *   В случае провала, возвращает `401 Unauthorized`.
3.  Написать Unit и интеграционные тесты.

**Break Point:**
*   Пользователь может зарегистрироваться и получить JWT токен.
*   Запросы к несуществующему защищенному эндпоинту (например, `/api/accounts`) с валидным токеном проходят через шлюз, а без токена или с неверным — получают ошибку `401`.

### Этап 2: Управление Счетами

**Цель:** Дать пользователям возможность создавать и просматривать свои банковские счета.

**Фокус:** `account-service`.

**Задачи:**
1.  Создать DTO для создания и отображения счета.
2.  Создать JPA-сущность `Account`.
3.  Создать `AccountRepository`.
4.  Создать `AccountController` с эндпоинтами: `POST /api/accounts` и `GET /api/accounts`.
5.  В сервисной логике реализовать проверку на `X-User-Id` из заголовка для всех операций.
6.  **Новое:** Реализовать эндпоинт `GET /api/accounts/{accountId}`, который будет использоваться для синхронной валидации в Этапе 3.

**Break Point:**
*   Пользователь с валидным токеном может создавать и просматривать **только свои** счета.
*   Запрос `GET /api/accounts/{accountId}` возвращает данные счета его владельцу.

---

### Этап 3: Ядро Транзакции (Асинхронная Сага)

**Цель:** Реализовать отказоустойчивый процесс перевода денег.

**Фокус:** `transaction-service`, `account-service`.

**Задачи:**
1.  **В `transaction-service`:**
    *   Создать JPA-сущности `Transaction` и `Outbox`.
    *   Реализовать логику `POST /api/transactions/transfer`: синхронный вызов `AccountServiceClient` для валидации, затем создание `Transaction` и атомарная запись в `outbox`.
    *   **Новое (уточнено):** Реализовать/настроить компонент-публишер для надежной отправки событий из `outbox` таблицы в Kafka.
    *   Реализовать Kafka-консьюмеры для оркестрации саги и логику компенсирующих транзакций.
2.  **В `account-service`:**
    *   Реализовать Kafka-консьюмеры для команд `DebitFunds` и `CreditFunds`.
    *   **Новое:** Реализовать **идемпотентную** обработку команд (например, проверяя `commandId` в кэше Redis или специальной таблице `inbox`, чтобы избежать двойного списания).
    *   Реализовать логику изменения баланса и отправки ответных событий через свой `outbox`.

**Break Point:**
*   `POST` запрос на `/api/transactions/transfer` корректно меняет балансы на двух счетах.
*   Статус транзакции в итоге `COMPLETED`.
*   Повторная отправка одного и того же сообщения из Kafka не приводит к двойному списанию/зачислению.

### Этап 4: Запросы и Уведомления

**Цель:** Предоставить пользователю историю операций и реализовать систему уведомлений.

**Фокус:** `history-service`, `notification-service`.

**Задачи:**
1.  **В `history-service`:**
    *   **Новое (уточнено):** Спроектировать и создать **денормализованную** таблицу `transaction_history` через Liquibase.
    *   Реализовать идемпотентный Kafka-консьюмер для событий `TransactionCompleted` и `TransactionFailed`.
    *   Реализовать эндпоинт `GET /api/history` с DTO для ответа.
2.  **В `notification-service`:**
    *   Реализовать идемпотентные Kafka-консьюмеры и логирование.

**Break Point:**
*   После завершения транзакции, в `history-service` появляется корректная запись.
*   Запрос истории операций работает.
*   Логи `notification-service` подтверждают получение событий.

### Этап 5: Дополнительный Функционал

**Цель:** Добавить аналитику и платежи по расписанию.

**Фокус:** `analytics-service`, `scheduler-service`.

**Задачи:**
1.  **В `analytics-service`:**
    *   **Новое (уточнено):** Реализовать Kafka-консьюмер, который накапливает события в буфер и выполняет **пакетную вставку (batch insert)** данных в ClickHouse через JDBC, чтобы минимизировать нагрузку.
2.  **В `scheduler-service`:**
    *   Реализовать эндпоинты для управления расписаниями.
    *   **Новое (уточнено):** Настроить Quartz Job с **персистентным хранилищем (Job Store)**, чтобы задачи не терялись при перезапуске сервиса.

**Break Point:**
*   Данные по транзакциям эффективно загружаются и доступны в ClickHouse.
*   Запланированный платеж исполняется ровно один раз, даже после перезапуска `scheduler-service`.

### Этап 6: Observability и Финализация

**Цель:** Сделать систему прозрачной, стабильной и готовой к показу.

**Фокус:** Prometheus, Grafana, Jaeger/Tempo.

**Задачи:**
1.  Настроить дашборды в Grafana.
2.  **Новое:** Настроить **алерты** в Grafana на критические метрики (например, высокий `consumer lag` в Kafka, рост числа HTTP 500 ошибок).
3.  Проверить и убедиться в корректности сквозной трассировки в Jaeger/Tempo.
4.  Финальное ревью кода, рефакторинг, расширение покрытия тестами.

**Break Point:**
*   Проект полностью функционален, стабилен, наблюдаем и готов для демонстрации в портфолио.
