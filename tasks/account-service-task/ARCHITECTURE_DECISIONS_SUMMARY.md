# Итоги и Архитектурные Решения для `account-service`

Этот документ суммирует ключевые архитектурные решения, принятые в ходе нашей дискуссии, и проблемы, которые они решают.

### 1. Основной принцип: "Чистая" Гексагональная Архитектура

**Решение:** Мы строго придерживаемся архитектуры "Порты и Адаптеры", чтобы полностью изолировать ядро бизнес-логики от
внешних технологий (веб, базы данных, Kafka). Зависимости направлены только внутрь: `Адаптеры -> Порты -> Ядро`.

### 2. Разделение входящих портов (UseCases)

- **Проблема:** Единый интерфейс `AccountUseCase` смешивал бы разные по своей природе задачи (например, пользовательские
  запросы на создание счета и системные команды на изменение баланса), нарушая Принцип Разделения Интерфейсов.
- **Решение:** Мы разделили входящие порты по ролям:
    - `CreateAccountUseCase`: для создания счетов (используется веб-контроллером).
    - `GetAccountQuery`: для запросов на получение данных (используется веб-контроллером).
    - `UpdateAccountBalanceUseCase`: для изменения баланса (используется Kafka-консьюмером).

### 3. Изоляция ядра от форматов данных (DTO)

- **Проблема:** Как адаптеры (веб-контроллер, Kafka-консьюмер) должны передавать данные в ядро, не "загрязняя" его
  специфичными для технологии классами (REST DTO, Avro)?
- **Решение:**
    - **На входе:** Адаптеры преобразуют входящие DTO в "чистые" **объекты-команды** (`CreateAccountCommand`,
      `DebitAccountCommand`), которые принадлежат ядру (`application.port.in`). Сервис работает только с ними.
    - **На выходе:** Сервис возвращает чистый **доменный объект** (`Account`). Преобразование в DTO для ответа (
      `AccountResponse`) происходит в слое адаптера (в контроллере).

### 4. Проброс сквозного контекста (Correlation ID и Трассировка)

- **Проблема:** Как отслеживать всю цепочку вызовов в распределенной системе для отладки и мониторинга?
- **Решение:** Мы явно передаем контекст.
    - В объекты-команды (`DebitAccountCommand`) добавляется поле `MultiValueMap<String, String> headers`.
    - Входящий адаптер (`AccountCommandConsumer`) извлекает заголовки из сообщения Kafka и кладет их в это поле.
    - Сервис передает эти заголовки дальше в исходящее **доменное событие**.
    - **Почему не `ThreadLocal`?** Этот подход выбран как более явный, предсказуемый и легкий для тестирования.

### 5. "Богатые" доменные события и "Поздняя" сериализация

- **Проблема:** Что должно содержать событие, генерируемое сервисом? Должно ли оно быть сразу строкой JSON?
- **Решение:**
    - Сервис генерирует "богатое" **доменное событие** (`AccountDebitedDomainEvent`) — строго типизированный объект со
      всеми бизнес-данными (сумма, новый баланс) и контекстом (correlationId, headers).
    - **Сериализация в JSON** (превращение в строку) происходит в **самый последний момент**, на границе системы —
      внутри исходящего адаптера (`OutboxPersistenceAdapter`). Это сохраняет ядро чистым и типобезопасным.

### 6. Именование и реализация `EventPublisher`

- **Проблема:** Название `EventPublisher` вызывало путаницу, так как его реализация не публикует событие в Kafka
  напрямую, а сохраняет его в `outbox`.
- **Решение:** Мы уточнили терминологию.
    - **Порт (`DomainEventDispatcher`):** Интерфейс, который видит сервис. Его имя отражает **бизнес-намерение** ("
      отправить событие на дальнейшую обработку").
    - **Адаптер (`OutboxPersistenceAdapter`):** Класс, реализующий этот порт. Его имя отражает **технический механизм
      ** ("сохранение в `outbox`").

### 7. Реализация `Inbox`/`Outbox` репозиториев

- **Проблема:** Нужно ли для `InboxRepository` и `OutboxRepository` создавать полную цепочку (Порт -> Адаптер ->
  JpaRepository) или можно пойти на упрощение?
- **Решение:** Мы обсудили оба подхода. Для сохранения максимальной чистоты и последовательности было решено
  придерживаться **"чистого" пути**, создавая отдельные интерфейсы-порты для этих технических репозиториев и отдельные
  классы-адаптеры для них.
