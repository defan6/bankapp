# Архитектура Проекта "BankApp"

Этот документ описывает высокоуровневую архитектуру, принятую для микросервисов в рамках проекта. Цель — обеспечить
создание гибких, тестируемых и легко поддерживаемых сервисов.

## 1. Основной Подход: Гексагональная Архитектура (Порты и Адаптеры)

Мы используем гексагональную архитектуру, чтобы изолировать ядро бизнес-логики от внешних технологий и систем.

- **Ядро (The Hexagon):** Находится в пакетах `domain` и `application`. Содержит чистую бизнес-логику, модели и правила.
  Не зависит ни от каких фреймворков.
- **Порты (Ports):** Это интерфейсы в пакете `application.port`. Они определяют контракты, через которые ядро общается с
  внешним миром.
    - **Входящие порты (Inbound):** API бизнес-логики, который вызывается извне (например, `AccountUseCase`).
    - **Исходящие порты (Outbound):** Контракты для взаимодействия с внешними системами (например, `AccountRepository`,
      `EventPublisher`).
- **Адаптеры (Adapters):** Находятся в пакете `adapters`. Это "переходники" к конкретным технологиям, которые реализуют
  или используют порты.

## 2. Ключевое Правило: Направление Зависимостей

> Зависимости в коде могут быть направлены **только внутрь**: от внешних, технологических слоев (адаптеры) к внутренним,
> абстрактным (порты, домен).

Это значит, что бизнес-логика (`application`, `domain`) **никогда** не должна импортировать или зависеть от классов из
`adapters`. Технологии зависят от бизнес-логики, а не наоборот.

## 3. Структура Сервиса (на примере `account-service`)

Каждый микросервис в проекте должен придерживаться следующей структуры:

```
com.bankapp.accountservice
├── AccountServiceApplication.java      // Главный класс Spring Boot
│
├── adapters                          // АДАПТЕРЫ (мосты к технологиям)
│   ├── in                              // Входящие (управляют приложением)
│   │   ├── web                         // --- REST API
│   │   │   └── AccountController.java
│   │   └── messaging                   // --- Сообщения из Kafka
│   │       └── AccountCommandConsumer.java
│   │
│   └── out                             // Исходящие (используются приложением)
│       ├── jpa                         // --- Работа с БД через JPA
│       │   ├── AccountJpaRepository.java // Интерфейс Spring Data
│       │   ├── AccountDbo.java         // JPA Entity
│       │   └── AccountPersistenceAdapter.java // Реализация порта AccountRepository
│       │
│       └── messaging                   // --- Отправка сообщений в Kafka
│           └── OutboxMessageRelay.java // Процесс, читающий outbox
│
├── application                       // ЯДРО: Оркестрация
│   ├── port                            // ПОРТЫ (интерфейсы-контракты)
│   │   ├── in                          // --- API бизнес-логики
│   │   │   └── AccountUseCase.java
│   │   └── out                         // --- Контракты для внешних систем
│   │       ├── AccountRepository.java
│   │       └── EventPublisher.java
│   │
│   └── service                         // Реализация бизнес-логики
│       └── AccountServiceImpl.java     // Содержит основную логику, не зависит от технологий
│
├── domain                            // ЯДРО: Бизнес-сущности и правила
│   ├── model                           // Доменные модели (чистые POJO)
│   │   ├── Account.java
│   │   └── Money.java
│   │
│   └── exception                       // Бизнес-исключения
│       ├── AccountNotFoundException.java
│       └── InsufficientFundsException.java
│
└── config                            // Конфигурация Spring
```

## 4. Пример Жизненного Цикла Запроса: Списание Средств

Рассмотрим, как архитектура работает на практике.

1. **Входящий Адаптер (`AccountCommandConsumer`):**
    * **Что делает:** Принимает сообщение `DebitFundsCommand` из Kafka.
    * **Роль:** Адаптирует "мир Kafka" к нашему приложению. Он не знает правил списания.
    * **Действие:** Вызывает метод `debitFunds()` у **входящего порта** `AccountUseCase`.

2. **Ядро, часть 1 (`AccountServiceImpl`):**
    * **Что делает:** Реализует `AccountUseCase` и содержит основную логику.
    * **Роль:** Оркестрирует весь процесс.
    * **Действие:**
        1. Вызывает **исходящий порт** `InboxRepository` для проверки идемпотентности.
        2. Вызывает **исходящий порт** `AccountRepository`, чтобы найти счет в базе данных.
        3. Выполняет бизнес-правила на **доменной модели** `Account` (проверяет баланс).
        4. Вызывает **исходящий порт** `AccountRepository` снова, чтобы сохранить измененный счет.
        5. Вызывает **исходящий порт** `EventPublisher` для публикации события `FundsDebited`.

3. **Исходящие Адаптеры (`AccountPersistenceAdapter`, `OutboxPersistenceAdapter`):**
    * **Что делают:** Реализуют исходящие порты `AccountRepository` и `EventPublisher`.
    * **Роль:** Адаптируют абстрактные запросы ядра ("сохрани счет", "опубликуй событие") к конкретной технологии (JPA).
    * **Действие:** `AccountPersistenceAdapter` преобразует доменную модель `Account` в `AccountDbo` и сохраняет через
      `JpaRepository`. `OutboxPersistenceAdapter` сохраняет событие в таблицу `outbox`. Вся эта группа адаптеров
      работает в одной транзакции.

4. **Исходящий Адаптер (`OutboxMessageRelay`):**
    * **Что делает:** В отдельном фоновом процессе читает таблицу `outbox`.
    * **Роль:** Асинхронно доставляет события, сохраненные в `outbox`, до конечного получателя.
    * **Действие:** Отправляет сообщение в Kafka с помощью `KafkaTemplate`.

Таким образом, ядро бизнес-логики остается чистым и изолированным, а вся "грязная" работа с технологиями вынесена в
сменные компоненты-адаптеры.
